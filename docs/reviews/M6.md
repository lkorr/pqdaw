## Summary verdict

**M6 is broad and mostly well built, but it should not close before C1, C2 and the High items are fixed.**

What is good:
- **The realtime design holds up.**
  - Everything on the audio thread checked out under a skeptical read: the recorder's rings (acquire / release, producer frames before the segment, indices on separate lines), `LiveInput` (bounded by ring capacity and 1024 held notes, room always kept for note-offs), `CaptureRing`, `CaptureFifo` on the WASAPI render thread (≤ 64 packets per wake, never blocks), and the stretch pool (free lists only on the audio thread, capacity reserved).
  - Every probe ran with 0 RtScope violations.
- **PDC is PF.5-compatible.** Delay lines, clip lines and event delays belong to the reader unit. A line reads only a bus its unit already reads (`setCompensation` refuses a producer that is not earlier) and that bus's silent flag. No new DAG edge, no shared scratch. One caveat is L7.
- **The two note worlds are clean.** Hz is never quantised: the 128-entry table holds `PitchId::fromCents` from double Hz, and the ring and record tap carry the full `PitchId`. A 12-TET Hz map plus bend stores 937.5 ¢ (off-grid, as it should). Live Keys notes equal drawn ones bit for bit (`test_live_input.cpp:169`).
- **Crash-safe WAV holds.** Killed at 50 / 700 / 1300 / 2900 / 4100 ms, every file was readable, 0 wrong samples, ≤ 0.81 s lost.
- **Block-size independence is fixed.** The M5 review's M3 (Re-Pitch depends on block size) is gone: Re-Pitch with markers, a loop and a tempo ramp, and Beats / Tones / Texture, are bit-identical at blocks 32 / 37 / 64 / 333 / 1024. The exception is C2.
- **The timing claims hold**: Beats ±0.146 ms (claimed ±0.15), Tones 0.006 ¢ on a sine, Complex onsets ≤ 2.17 ms (claimed ±2.5), the count-in, metronome-to-PDC alignment, and the tail through the silence rule.
- **The CPU numbers meet the plan**, except PDC per input (58.6 ns against 40, known) and the audio/64 regression (M13).

What is wrong, in four clusters:
1. **Recorded audio in a saved project can be deleted (C1, H1).** The "Unsaved" recordings folder belongs to the process, not to the untitled document. Two cases:
   - Save while a take is recording, or save after undoing a recording and then redo. Either way the saved project keeps referencing the folder, and the next untitled New / Open / Quit runs `remove_all` on it.
   - Saving a project inside that folder.
2. **Complex / Complex Pro (C2, H2, M10).**
   - At an engine block × pitch rate below about 35, the voice re-primes its stretcher every block. This happens at −10 st and below, or with 48 kHz files in a 96 kHz project. The result is clicks and 10× CPU spikes.
   - With more than 16 Complex tracks, clips silently play as Tones.
   - Voices started together spike together every 30 ms.
3. **PDC edges (M1–M3).**
   - Shifted automation is wrong for `shift` frames after every loop wrap.
   - Growing delay lines costs 1.2 ms in one block.
   - A line dropped by one plan is forgotten by the next, even mid-fade.
4. **Smaller recording and identity gaps (M4–M9).**
   - Loop + punch loses `offset` frames per pass.
   - A bent Hz note is re-frozen in the tuning at Capture or commit time, not the one it was played in.
   - WASAPI clock drift glitches recordings.
   - Recordings over 4 GiB.
   - Recording writes run under a mutex on the pool's disk thread.

Tempo detection (H3) makes confident octave and 2/3 errors on common loops.

**Counts:** 2 Critical, 3 High, 13 Medium, 23 Low.
- C1, C2 and H1–H3 are verified by probes, and I re-read both Criticals.
- Every fix is small or medium.

**Recommendation:** before closing M6, run one fix task for C1, C2, H1–H3, plus M1, M3, M4 and M5, which are cheap. Bisect M13 (+21 % on audio/64 since M5) separately. Then re-run `-Affected -Slow` and the warp / playback ship benches.

- **Critical**: silent wrong output, or loss of user data, in ordinary use; or memory unsafety on the audio thread in ordinary use.
- **High**: wrong or unsafe behaviour a user will hit, or a crash on untrusted input.

## PF.5 compatibility of the compensation plan

**Compatible**, with one caveat (L7). Checked in `project_program.cpp:860-924, 1135-1190` and `latency_plan.*` (the PDC sub-reviewer and I):
- **Reader-owned state.** Delay lines are looked up only in the same unit's previous plan entry (`addLine` / `prevLine`). Clip lines live in the unit's own clip table (`Entry::clipIn`). Each voice unit owns its own `EventDelay`. Fade blocks are per line, and `zeros_` is read-only.
- **No new edge.** A line reads only a bus its unit already reads, and `setCompensation` refuses one whose producer is not earlier in unit order (`:866`). It also reads that bus's `silent` flag, written by the producer on the same existing edge, and the clip player's `clipIn` / `clipActive`, written once per block by the timeline hook before any unit runs.
- **Serial switching.** `maybeSwitchCompensation` adopts plans at the block boundary, outside the unit loop. Live audio input (`track.in`) is not delayed.
