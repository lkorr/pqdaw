## 1. The cache key includes per-instance resource slots

- **Evidence.** With `PQ_JIT_STATS` on, `pq_bench_playback "mixer/64x8 notes jit"` (64 MIDI tracks with the default
  instrument plus 8 returns) ran **130 compiles**: 64 quick-first images, 64 final images and 2 others. Each compile had a
  different key. The optimised IR of 63 of the 64 units was byte-identical once the key-named function prefix was
  normalised (`PQ_JIT_DUMP` + md5). Printing a hash after each section of `codegenDigest` showed the difference was in the
  ops section. `src/jit/src/cache.cpp:166` hashes `x.resource`, which is a per-instance slot (meta frame table, GU.1
  curve, tuning table). Code generation reads only `resource != kNone` (`codegen.cpp:1946`). The resource pointer reaches
  the code through a pointer-table slot (`jit_image.cpp:211` → `L.opInfo`), and `L.opInfo` is already hashed, so the
  aliasing pattern stays in the key.
- **Experiment.** Hash `uint32_t(x.resource != g::kNone)` instead. Result: **6 compiles, 318 ms of compile instead of
  6776 ms**. The block cost fell from 152.7 to 138.3 µs, because 64 copies of the same code no longer compete for the
  instruction cache.
- **Also helps.** The disk cache and the AOT seed. Today a stock instrument seeded at one slot misses on any other slot,
  so the seed rarely hits in user projects.
- **Proposal.** Hash only whether a resource is present, as T5.4 already does for `External::clip`. Add a
  `CacheConfig::verify` test: two tracks with the same instrument share code (memory hit), and the audio is the same.
- Gain: very large on cold open and duplicate tracks. Risk: low (L.opInfo still keys the slot pattern). Effort: one line
  plus a test. Core change: no.

## 2. Project patch re-layout is quadratic (S-drag 614 ms)

- **Evidence.** Timers in `rebuild()` and `Builder::run()`, during the TX.resize perf test (64 tracks, 75 bands,
  350 groups, 629 nodes, **8539 project wires**). The model build took 518–561 ms out of a 614 ms step; lowering 0,
  scene 0.75 ms, `setScene` 1.5 ms. Inside the model build:
  - the closed-group wire loops took **371 ms** over 286 groups. `model.cpp:584` and `:599` loop over
    `doc::wiresOf(p)` (every wire in the project) for each closed group. `kidOf` scans the kids linearly and calls
    `doc::groupContains`.
  - `circuitLayout` took **118 ms** over 64 opened groups. `model.cpp:670` → `:416` loops over all project wires again
    and runs `graph::autoLayout` for each opened group.
  - `addedControl` (`model.cpp:459`) took another 3 passes over all wires per panel group (6 ms).
  - `controlAnchor` 0.13 ms, `deviceNode` 6 ms, `findRacks` 6 ms: negligible.
- **Proposal.**
  - Index the wires once per build: by track, and by device to its kid or box.
  - Iterate only the group's own track's wires (about 130 instead of 8539).
  - Cache each opened group's inner `autoLayout` by a key of member sizes and wires. One block's rescale leaves every
    other group's interior unchanged.
  - Later: re-lay out only the band whose block changed.
- **Gain.** 540 ms → about 20–50 ms (estimate: 490 ms of the 540 are in the loops above). `rebuild()` also runs on every
  structural edit, every nudge and every drop, so a 64-track project currently stalls the UI for about half a second
  on any edit.
- Risk: low. Effort: S. Core change: no.

## 3. Far LOD paints every panel live

- **Evidence.** In the fitted 64-track frame, `CircuitCanvas::paint` took 8.9–9.6 ms and emitted **783,848 vertices**:
  `panelsPainted=361`, `chunksFromTiles=24`, nodes, wires and faces 0. The project canvas hooks (underlay, lanes,
  overlays) took 0.13 ms together. The static layers can come from tiles, but `paintJacks` and `paintLive`
  (`circuit_canvas.cpp:633-641`) run for every visible panel at every LOD. That is about 2.2k vertices per panel, even
  when a panel is a few pixels wide.
- **Proposal.** Below a pixel-size threshold, skip the live and jack layers or draw a flat rect. Alternatively, bake the
  panels into the Far chunk tiles and invalidate a chunk when one of its panels' values changes.
- **Gain.** 9 ms → under 1 ms; the test's budget is 2 ms. Risk: low; a golden may move at Far zoom. Effort: S. Core
  change: no.

## 4. Disable LSR in the JIT's codegen pipeline

- **Evidence: compile time.** `-time-passes` on one fixture unit (11.4k IR instructions, 465 ms):
  - X86 DAG ISel 33 %
  - Greedy RA 21 %
  - **Loop Strength Reduction 15 %** + IV Users 3.4 %
  - MI scheduler 4 %

  Machine code is 85–90 % of every compile. The IR passes (the light pipeline) are about 8 %; codegen to IR and the host
  are 2 %.
- **Evidence: A/B** (`PQ_LLVM_ARGS`, `pq_bench_project`, interleaved, load 7–26 %):

  | Flags | Per-unit JIT, 32 units | Steady state |
  |---|---|---|
  | baseline | 7437 / 7502 / 7936 ms | 379–384 µs/block |
  | `-disable-lsr` | 5480 / 5818 / 5899 ms | 379–397 µs/block |
  | `-disable-lsr -fast-isel` | 4473 ms | 394 µs/block |
  | `-enable-misched=false` | 7142 ms | (not worth it) |

  `pq_bench_render` was unchanged within noise: fm_voice, pluck, drive_zdf, stereo_echo, noise_tables, the Operator
  stock-default/full/spread x64, full x64 moving, and patch32 x64 per block (306/293 vs 313/354 ns). Operator compiles
  are only −2–4 %; LSR matters for the long global effect stages.
- **Proposal.** Set `disable-lsr` through `llvm::cl` in `initialiseLlvmOnce()` (`compiler.cpp:63`). Record ship rows in
  RESULTS.md (compile and run) before merging. Risk: low. Effort: XS. Core change: no.

## 5. Compile units in parallel

- **Evidence: everything is serial.**
  - `BackgroundCompiler` has a single worker thread (`background_compile.cpp:18,69`).
  - `Compiler::Session` holds one recursive mutex for the whole compile (`compiler.cpp:131`, `Session::Lock` in
    `compileImpl`).
  - The process uses one compiler (`compile/image.cpp:36`).
- **Experiment.** K threads, each with its own `jit::Compiler`, compiling the fixture's 32 units:

  | Threads | Wall time | Wall time with `-disable-lsr` |
  |---|---|---|
  | 1 | 7574 ms | 5362 ms |
  | 2 | 4037 ms | 2772 ms |
  | 4 | 2487 ms | 1676 ms |
  | 6 | 1652 ms | 1241 ms |
  | 8 | 1439 ms | 1068 ms |

- **Benefits.** Cold open of an uncached project, topology rebuilds, rate changes, and edits that touch several units.
  A single-unit edit gains nothing from this (see #7).
- **Proposal.** N background workers (≈ cores − 2, below normal priority), each with its own session. They share the
  disk cache directory (writes are already atomic and multi-process safe) and an in-memory key → code map. Alternatively,
  one LLJIT with `setSupportConcurrentCompilation`; that needs per-compile capture state instead of `Session::objectBytes`
  / `captured` and a TargetMachine per thread for the IR pipeline.
- **Risk.** Memory, since each LLVM context and session holds tens of MB. The L10 poisoning logic becomes per session.
  The order of deliveries must stay as `ProjectLink` expects.
- Effort: M. Core change: no document or engine structure, but the JIT threading model changes: worth a 5-line design
  note to the user.

## 6. The ramp-mode copy doubles the stage code

- **Evidence.** IR instructions per function (`PQ_JIT_STATS`):
  - Fixture unit: `stage2` 4312 vs `stage2_ramps` 4575; `stage1` 539 vs `stage1_ramps` 808. The ramp copies are about
    45 % of the unit's 11.4k instructions.
  - Default instrument: `stage1` 405 vs `stage1_ramps` 1164; `stage2` 458 vs `stage2_ramps` 753.
  - 100-step chain with one param: `stage0` 1742 vs `stage0_ramps` 1840. The chain now takes 64 ms to compile, against
    37–57 ms before TX.smooth. The 1000-step chain now has 34.8k IR instructions, against 14.2k on 10-24.
- **Cause.** `codegen.cpp:617-664`: for any stage with ramps, `<stage>_ramps` re-emits every region after the ramps, even
  regions that read no ramp.
- **Proposals.**
  - (a) Emit a ramp-mode variant only for fused runs or regions that read a ramp, chosen by a per-run uniform branch.
    Unaffected runs are emitted once.
  - (b) Put the `_ramps` / `_rampmode` functions in their own module and compile them concurrently (with #7).
- **Gain.** Up to −45 % per-unit compile time. That is the edit → JIT latency the user feels, and the held-for-JIT edits
  (`interpretBudget` 0.25) wait for exactly this compile.
- **Risk.** The TX.smooth bit-exactness tests; the cost of ramp blocks while params move. Effort: M (b) to L (a). Core
  change: no.

## 7. Function-level parallel codegen inside one unit

- **Evidence.** In the fixture units, the largest function is 38–40 % of the IR (for example `stage2` 4312 of 11371).
  The rest is split over 4–8 functions.
- **Proposal.** One module per function family (stage, pair, ramps), compiled concurrently. ORC resolves the
  cross-module tail calls within one JITDylib.
- Gain: about 2–2.5× on a single-unit compile, for example 290 → about 120 ms (estimate, not measured). Effort: M.
  Combines with #5 and #6b.

## 8. FastISel for the quick first image

- **Evidence.** `-fast-isel` on top of `-disable-lsr`: 5480 → 4473 ms (−18 %), with run time 394 vs 380 µs/block.
- **Proposal.** Use it only for `quickFirst` images, which the refined image replaces with an Instant swap.
- **Risk.** That swap needs bit-identical output: check it with the existing interp == JIT and quick == final tests. No
  stack probes allowed. Effort: S.

## 9. Duplicate lowering on the UI thread

- `ProjectPatchView::rebuild()` calls `doc::lower` itself (`view.cpp:526`), although `ProjectLink` publishes its
  `LoweredProject` to `ViewContext::currentLowering()` (EQ.4b, `view_context.h:277`).
- Cost: 6.0–6.1 ms per structural edit at 64 tracks (GU.2's `pq_bench_project_patch` lower row).
- Proposal: use the shared lowering when its snapshot equals `built_`. Lower locally only when the link has not caught up
  (or wait for it, bounded).
- Effort: S. Risk: a serial mismatch shows a stale graph for one frame.

## 10. Executable hash on the first compile

- The first compile in each process showed `cache=15–22 ms` (`detail::binaryIdentity()`; 2 ms when T1b.4 recorded it,
  on a smaller binary).
- Proposal: compute it on a background thread at startup.

## 11. Engine threading (structural)

- The fixture's steady JIT state is 380 µs per 64-frame block, 28.5 % of one core, all on the single RT thread
  (`project_program.cpp:990`, a serial unit loop). SPEC §2 plans SCC-parallel execution for M12.
- Nothing cheap here. Listed so the 5–6× headroom is on record. **Needs user sign-off (core structure).**
- Not measured: the cost of a track whose 8-lane voice group holds one voice. `mixer/64x8 notes jit` is about
  33 ns per track-sample, while the Operator x64 is 1.4 ns per voice-sample. That suggests the lane utilisation is worth
  a look before M12.
